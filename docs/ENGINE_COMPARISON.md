# Трафарет, CSP и Krita: сравнение движков

Дата: 2026-11-18

## О границах сравнения

- **CSP (Clip Studio Paint)** — закрытый продукт: его внутренний код мы не оцениваем, сравниваем только публичные возможности.
- **Krita** — open source на C++/Qt/KDE: строки кода (LOC) несопоставимы с нашим проектом (web-стек), поэтому численное сравнение кодовой базы бессмысленно.
- **Трафарет (наш движок)** — специализированный рисовальный движок на Canvas2D с упором на лайнворк для тату.

## Объективно слабее

Ниже сохранён исходный аудит коммита `85ad144`; ссылки на строки относятся к
этому снимку. Актуальный статус исправлений P0 — в следующем разделе.

Честный список слабых мест — не абстрактных «хотелок», а конкретных находок по коду:

- **Монолит рендер-слоя**: `src/components/StudioCanvas.tsx` — 1337 строк в одном файле: рендеринг, интерактивность, состояние холста и история вперемешку. Мутации слоёв размазаны по точкам `StudioCanvas.tsx:570,580,588,639,844`.
- **История (undo/redo) — бюджет памяти, не кадра**: эвикция по `MAX_HISTORY_PIXELS` — `StudioCanvas.tsx:561-567`, redo-ветка — `StudioCanvas.tsx:677-695`. `redoRef` лежит вне `historySizeRef`/эвикции: redo-стек не учитывается в бюджете и не эвиктится. Заявления о тяжёлом клонировании/фризах без профиля не делаем.
- **Геометрия**: расчёт дуги берёт `maxY` по `a[0]` вместо `a[1]` — правильно `a[1] + ry + pad` — `src/lib/vector.ts:36` (потенциально неверный bbox дуги SVG).
- **Дублирование логики трансформаций**: одни и те же матрицы/повороты реализованы дважды — `StudioCanvas.tsx:179-200` и `vector.ts:60-93`.
- **Размазанная модель кистей**: union `BrushId` в `src/types.ts:2` плюс ID-ветки в `brushes.ts:147,170-173` — поведение кисти определяется ветвлением, а не данными.
- **Расхождение Canvas и SVG**: две параллельные реализации рендеринга форм — `vector.ts:95-141` (Canvas) и `vector.ts:163-211` (SVG) — правка в одной не попадает в другую.
- **Снапшот проекта**: мутирование кэша вместо чистой функции — доказано (`src/lib/project.ts:146-177`); стоимость `toDataURL` — требует профиля, без замеров не заявляем.
- **Конфликты синхронизации**: `conflict` обнуляется до `await` и не восстанавливается при ошибке — `src/lib/sync/engine.ts:156-196`.
- **Метаданные сборки**: `package.json` (строки 2, 4, 76) — расхождения в name/version/artifactName, мешает воспроизводимым релизам.

## Где наш код можно сделать эффективнее

Приоритизированный план (P0 → P1), вытекающий из находок выше:

**P0 — ЗАВЕРШЁН, дефекты исправлены с регрессионными тестами:**
- `vector.ts` — `maxY` дуги вычисляется через `a[1] + ry + pad`;
- история — undo и redo используют общий бюджет, очистка redo и удаление слоя корректно пересчитывают стоимость;
- конфликт — после ошибки разрешения восстанавливаются данные и статус конфликта, повторный выбор остаётся доступен;
- метаданные — `name: trafaret`, `version: 1.0.0`, lockfile синхронизирован, Windows-артефакт сохраняет опубликованное имя `Trafaret-Windows-x64.exe`.

Каждый фикс покрыт регрессионным тестом; всего 101 тест в 13 файлах.

**P1 — выделить глубокие модули, не поверхностные:**
- `history` — **ЗАВЕРШЁН**: `src/lib/history.ts` владеет общим undo+redo budget, переходами, инвалидацией redo и очисткой; 5 отдельных тестов модуля. Журнал операций вместо снапшотов — лишь кандидат после измерений, не предписание;
- `geometry` — **ЗАВЕРШЁН**: `src/lib/geometry.ts` содержит единые bounds, origin, прямые/обратные трансформации и параметры дуг для Canvas, SVG и анализа эскиза; 4 теста модуля;
- `stroke-session` — **ЗАВЕРШЁН**: `src/lib/stroke-session.ts` владеет давлением, сегментами, симметрией, raster rect и vector commit; рендеринг кистей управляется data-полями с legacy fallback; 7 новых тестов;
- `compositor` — **ЗАВЕРШЁН**: `src/lib/compositor.ts` владеет проходом слоёв, масками, clip-to-below, preview и временными buffers; 3 теста модуля плюс пиксельные E2E.

**Что явно НЕ делаем сейчас** (гипотезы до профилирования, не решения): тайловый рендеринг, dirty rects, бинарный формат снапшотов. И не раздробляем код на мелкие shallow-helpers «по одной функции на файл» — выделенные модули должны давать глубокий интерфейс и скрывать детали, а не переименовывать существующие функции.

## Что заимствовать

Берём идеи и механики, а не код — заимствование возможностей конкурентов, приоритизированное по ценности для tattoo linework.

**Сейчас** (прямой эффект на качество лайнворка):
- vector control points — редактируемые опорные точки векторных линий после отрисовки (CSP, Krita);
- line width redraw — локальное изменение толщины уже проведённой линии (CSP);
- brush presets — пользовательские пресеты кистей вместо фиксированных 7 BrushId;
- recovery / autosave — восстановление документа после сбоя (есть у CSP, у нас пробел; у Krita в официальном источнике не заявлено);
- predicted stroke — предсказание штриха для снижения воспринимаемой задержки пера;
- nondestructive ops — неразрушающие трансформации/эффекты поверх слоя, не копируя растр;
- print / color — печать и цветовые профили как часть пайплайна «эскиз → готовый трафарет».

**Позже** (цена внедрения выше, отдача для ниши ниже):
- PSD / ABR — импорт форматов конкурентов (пресеты кистей и документы);
- plugin API — расширяемость (Python у Krita; публичный API у CSP не заявляем);
- ICC — полноценный цветоменеджмент; сейчас у нас DPI/физический размер экспорта без полного ICC (простой CMYK-конверсии нет).

**Не нужно сейчас**: анимация, 3D, комиксы, многостраничные документы — это охват CSP/Krita вне нашей ниши.

**Лицензионное ограничение**: код Krita распространяется под GPL — копировать его напрямую без лицензионного решения нельзя (возможны copyleft-обязательства, нужна отдельная лицензионная проверка). Заимствуем только идеи и публичные спецификации форматов; реализация — наша. У CSP код закрыт — доступны только наблюдаемое поведение и публичная документация.

## Как доказать превосходство

Доминирование — это измерение на одинаковых условиях, а не вывод из LOC или списка фич. Методология:

- **Одинаковые входы**: те же документы, те же задачи, то же железо — и у нас, и у CSP/Krita;
- **p50/p95 pen latency** — задержка пера по перцентилям, не среднее (п95 ловит фризы истории и GC);
- **RSS + unique memory** — физическая память процесса и реально уникальные страницы, а не `performance.memory.usedJSHeapSize`;
- **чистовой linework time** — время до готового линейного рисунка, фиксированный художник и бриф;
- **print accuracy** — совпадение отпечатка с экранным макетом (геометрия, масштаб, цвет);
- **blind artist review** — слепое сравнение результата без подписи, какая программа чья.

### О сложности — два разных измерения

- **Сложность продукта** (охват): у нас она объективно ниже — нет анимации, 3D, комиксов, многостраничности. Меньший охват — осознанный выбор ниши, а не достижение.
- **Сложность разработки** (инструментарий): toolchain Krita сложнее нашего (C++/Qt/KDE, OpenGL/D3D11, ручная сборка, порты на 4 платформы). Но это не доказывает нашу эффективность: чужая инфраструктурная сложность не конвертируется в нашу производительность. Эффективность доказывается только замерами из раздела выше.
